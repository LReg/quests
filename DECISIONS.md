# Decisions

- **Build setup follows the chunkloader repo, not spec §2.1/2.2.** One Gradle build produces `questbook-<version>-mc26.2.jar` and `-mc26.3.jar` (custom `compileJava_<mc>` / `jar_<mc>` tasks, `mcVersions` list in `build.gradle.kts`). CI is a single `build.yml` that uploads both jars as artifact and attaches them to the GitHub release on `v*` tags. No ORAS/GHCR publishing, no matrix, no `-PmcVersion`. Per-version code goes into `src/mc<version>/java` (picked up automatically; none needed so far).
- Quest YAML saves in the editor are small atomic file writes done on the main thread (spec rule 3 asks for async); database I/O is fully async.
- REGION `baseY` is the editor's **feet block**, the same coordinate `Region.contains` compares (spec §5). `pos1` resets it, `pos2` lowers it if lower, so it ends up as the min of both. Only `baseY` is stored, not both corner heights. (An earlier version used the block below the feet, which made height 1 unreachable.)
- Advancements are registered with `Bukkit.getUnsafe().loadAdvancement`. If it throws, the feature disables itself and logs; no datapack fallback was written. Not verified on a live server: whether already-online players see newly registered advancements before relogging.
- Step-sign tag role: a sign that is both start sign and step sign keeps role `start`.
- Dialog callbacks are re-dispatched to the main thread.
- Chat capture for single-line input ends on the first message (`cancel` discards).
- Open questions (§17) use the defaults: English messages, `questbook.admin` defaults to ops, no draft markers. `questbook.editor` defaults to `true` (everybody) on request; servers that want it restricted set the node to false for the default group.
- Stale tags: signs no quest uses any more (file deleted by hand, step changed) lose their PDC tags when a player next right-clicks them. Until then they do not protect the sign, since protection looks at the quests, not the tag.
- `/reload` is not supported: the plugin logs a warning if players are online while it enables.
- Saving a change that leaves a published quest invalid (e.g. a SIGN step without a sign) drops it back to DRAFT and lists the problems, instead of rejecting the change. Players mid-quest then see "being rewritten" until it is fixed and republished.
- Text delivery is cancelled per quest run, never per player, so abandoning or testing one quest cannot freeze another.
- Advancements are registered parents first. Re-registering a quest also re-registers the quests below it, since the game drops children with their parent. Whether online players keep their progress for a re-registered advancement is unverified.
- Movement is evaluated in the move event itself (MONITOR, destination location) after an allocation-free check, instead of scheduling a task per block move.
- Paper builds stay unpinned (`.build.+`), like chunkloader.
- No unit test for the quest state machine and no MockBukkit tests: the service needs a live Bukkit. Pure logic is covered.
- Validation messages and editor error reasons (e.g. "max 50 steps") stay English in code as diagnostics. All menu and player text is in `messages.yml`.
- Sign protection also covers the support block, pistons and flowing liquids, since a sign drops without its support. Editors may still remove a support block.
- Deleting a quest removes it from the `requires` of quests that needed it (they would be locked forever otherwise).
- Unknown trigger types, dimensions and advancement keys in hand-edited YAML load the quest as DRAFT with a logged problem, never as another trigger.
- `/qe reload` reconciles online players' runs: clamps steps, drops vanished quests (also test runs and editor selections), disarms runs of quests that are drafts now, and restarts the step text only for runs that waited for publication or whose current step changed. A run mid-delivery of an unchanged step is left alone. The command lists what only applies after a restart (advancements of changed/unpublished quests, `preview.interval_ticks`, `advancements.enabled`). It still runs on the main thread.
- Waxed signs cannot be edited by anyone, so the spec's "editors sneak + right-click to edit text" (§8.4) only lets editors reach the sign without triggering the quest; to change the text, unlink first.
- Not done: re-delivering a step when an editor moves or removes steps under a live player (spec says keep the index); `dialogs.enabled` is re-read on reload, but `preview.interval_ticks` and turning `advancements.enabled` off need a restart.
- Steps have two texts: `text` (told when the step starts, before the trigger) and an optional `after` (told when the trigger has fired, before the next step or, for the last step, before the completion title). Changes the spec's one-text step. The YAML key `after` is optional, so existing quest files load unchanged and need no migration. `/qe step after <id> <n>` and a book icon in the step menu edit it.
- Advancements: Paper's `loadAdvancement` refuses to replace a loaded advancement and `removeAdvancement` only deletes its file, so a running server can add but not change or drop one. Changed or unpublished quests apply after the next restart; the hash of what was written is kept in `advancements.yml` so unchanged quests are left alone. (The earlier remove-then-load logged "already exists" and could leave the advancement missing on alternate restarts.)
- KILL trigger (added on request, not in the spec): `{type: KILL, target: ANY|ANIMAL|MONSTER|PLAYER|<ENTITY_TYPE>, amount: 1..1000}`. Counts kills by a player (final blow, arrows included, MONITOR priority), only while the step is armed. The count lives in memory per run, so it restarts at 0 after a relog or restart. Persisting it would need a new column in `progress`.
- Quest ownership (added on request): every quest stores `owner` (UUID of its creator). Editors only see and edit their own quests: `/qe`, `/qe list`, tab completion, the GUI, test mode, stats and the start/step signs of other quests are hidden or protected from them. Someone else's quest answers as "unknown quest". Admins (`questbook.admin`, op by default) see and edit everything and can hand a quest over with `/qe owner <id> [player]`. Files from before ownership have no owner: they count as owned by the editor named in `author` and get the owner stamped on their next save; otherwise only admins can edit them. Players are not affected, published quests stay visible in the game as before.
- Start signs must be empty on both sides when linked (`editor-sign-not-empty`). Linking waxes the sign and protects it from breaking, and every player is an editor by default, so otherwise anybody could lock another player's written sign. A sign already used as a step sign cannot become a start sign, and a start sign cannot become a step sign. Step signs keep their text (players read it), so they are only checked for ownership: an editor cannot link a sign that another editor's quest uses.
- **Branching (1.2, from the "Branching & Conditions Plan" artifact).** Every step keeps going to the following step; a step can have up to 4 conditions ("if … → step/end", first true wins) and an "otherwise" target (`next`, null = following step). Endings are targets (`next: end` / `goto: end` plus `ending:`), not a separate step flag. The editor sees one **Then…** menu per step instead of the plan's three icons (Next step, Conditions, Ending), because all three answered "where does the player go now". The step menu is grouped into rows: reads (text, after, hint, other texts), does (trigger and its settings), then.
- Steps and CHOICE/WORLD CHOICE options have hidden ids (`s4`, `o2`) assigned by the model when missing, so 1.1 files load unchanged and moving steps or renaming buttons never breaks a reference. New ids are max+1, so a deleted id is not handed out again while higher ids exist. Edits that leave a condition or jump pointing at a removed step, button or answer drop it and tell the editor (`editor-refs-dropped`).
- Conditions are picked, never typed: buttons and world-choice outcomes of any step of the quest, answers of ANSWER steps with at least two answers (stored normalized), an item from the editor's hand (amount), and choices or endings of another quest (from that quest's progress row). Right-click negates.
- Progress keeps the step index as before. Choices, the path (step ids, last 200) and the ending of the last completion live in a new table `progress_extra`, not in new columns, so the 1.1 jar can still write `progress` with its 8-value INSERT after a downgrade. A replay clears choices and path but keeps the last ending until a new completion. Runs from before 1.2 get their path seeded as steps 1..current on join (quests were linear then).
- Requires can demand an ending (`requires_endings: {quest: ending}`); the locked message does not reveal which ending.
- WORLD CHOICE (`FIRST_OF`) options may only use world triggers (REACH, REGION, SIGN, INTERACT, DIMENSION, ADVANCEMENT, KILL, and since 1.3 HAVE_ITEM and PLACE); kill counts are per option. CHOICE buttons are chat buttons (like Continue) and `/quest choose` lines in the journal; no dialog.
- Player guide per quest (`guide: {particles, compass}`, on by default since 1.3; a 1.1 file without `guide:` gets the default, a 1.2.0 file without it (recognised by its step ids) had the guide off, since 1.2.0 only wrote the key when on; the setting is now always written on save): particles reuse the editor preview outlines; the compass bar is a boss bar whose title is a strip of N/E/S/W, ticks and a marker, updated every `guide.interval_ticks`. It follows the quest picked with [Track] in the journal, else the first run with the compass on. Steps without a place (CONTINUE, ANSWER, CHOICE, KILL, DIMENSION, ADVANCEMENT, HAVE_ITEM, PLACE without an area) show no bar.
- Summary limit 1000 (600 in 1.2.0) and line breaks kept; all limits in `config.yml limits:`. The advancement description stays the old one-line text for summaries up to 200 characters (so 1.1 quests are not "changed" and need no restart), longer ones are cut at 200.
- The branch map is a 6-row chest: steps left to right in list order (two columns each), main path on the top row, condition-only paths on rows below (max 3 rows), lines as glass panes. Jumps back and endings are in the tooltips, not drawn.
- **The plugin never takes or changes a player's items (1.3).** "Has an item" conditions and the HAVE_ITEM trigger only look at the inventory. The `take` option of 1.2 is gone: files that still say `take: true` load normally, the key is ignored with a log line, and saving drops it. Questbook stays non-invasive: it reads the world and the player, it does not change them.
- `progress_extra.run_at` (1.3) holds `progress.updated_at` of the moment the row was written. A 1.1 jar run in between updates `progress` but not `progress_extra`; on load a mismatch marks the run part (choices, path) as stale and it is ignored, so going back to 1.1 and up again never moves a player to an old step. Rows from 1.2.0 have no `run_at` and are trusted. Broken values in the table are skipped instead of failing the whole player load.
- PLACE counts only placements the server keeps (`BlockPlaceEvent` not cancelled and `canBuild()`), each spot once per step. Its area is a REGION box edited with the same buttons.
